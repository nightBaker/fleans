<Section title="Execution model" id="execution">
  <Fragment slot="intro">
    How a workflow instance runs, survives failure, and stays fast.
  </Fragment>

  <SpecRow tags={['grain', 'actor']} title="Actors, not orchestrators">
    Every workflow is an independent Orleans grain. No shared coordinator, no lock contention — add silos, get linear throughput.

    <Fragment slot="note">Each instance activates on whichever silo Orleans places it, so throughput grows with the cluster.</Fragment>
  </SpecRow>

  <SpecRow tags={['journal', 'replay']} title="Event-sourced, crash-safe state" href="/fleans/concepts/architecture/#reliability">
    Append-only event log with deterministic replay. Silo dies mid-workflow? Orleans reactivates the grain on another silo — no orphaned state.

    <Fragment slot="note">State is rebuilt from the journal on activation.</Fragment>
  </SpecRow>

  <SpecRow tags={['memory', 'batch']} title="In-memory hot path">
    Active workflows run from RAM — mid-workflow steps skip the database. Events batch into one transaction at the end of each grain call.

    <Fragment slot="note">One write per grain call, however many activities it advanced.</Fragment>
  </SpecRow>

  <SpecRow tags={['bpmn', 'errors']} title="Typed BPMN recovery paths" href="/fleans/guides/error-handling/">
    Compensation, error boundaries, and escalation events are first-class. Failure modes get explicit semantics, not ad-hoc try/catch.

    <Fragment slot="note">Recovery lives in the diagram, where reviewers can see it.</Fragment>
  </SpecRow>
</Section>

<Section title="Data &amp; operations" id="operations">
  <Fragment slot="intro">
    Reads, storage and transport are split so each can scale or be swapped on its own.
  </Fragment>

  <SpecRow tags={['cqrs', 'replica']} title="Scale reads separately from writes" href="/fleans/concepts/architecture/#scalability">
    Built-in CQRS split routes read traffic through a NoTracking query context and an optional PostgreSQL replica.

    <Fragment slot="note">Point queries at a replica without touching the write path.</Fragment>
  </SpecRow>

  <SpecRow tags={['projection', 'ef']} title="Materialized read projections">
    Admin UI and state queries read a pre-built EF projection. No event replay to render a list or poll for completion.

    <Fragment slot="note">Listing instances never replays a journal.</Fragment>
  </SpecRow>

  <SpecRow tags={['sqlite', 'postgres']} title="Bring your own database" href="/fleans/reference/persistence/">
    SQLite for laptops, PostgreSQL for production — selected at startup via a single config key, no code change. The provider model is open if you need to add another.

    <Fragment slot="note">`Persistence:Provider` picks SQLite (default) or PostgreSQL.</Fragment>
  </SpecRow>

  <SpecRow tags={['streams', 'kafka']} title="Plug in your stream provider" href="/fleans/reference/streaming/">
    Domain events flow through Orleans Streams. Flip `Fleans:Streaming:Provider=kafka` to use the bundled Kafka adapter for cross-silo durability — or ship your own provider against the same extension point.

    <Fragment slot="note">In-memory by default; Kafka for durable cross-silo delivery.</Fragment>
  </SpecRow>

  <SpecRow tags={['docker', 'helm']} title="Run in your infrastructure" href="/fleans/reference/self-hosting/">
    Fleans ships as a container image you can run anywhere — laptop, VM, or Kubernetes. Your data never leaves your network, and there is no SaaS dependency to ramp.

    <Fragment slot="note">Docker Compose bundle and Helm chart on every release.</Fragment>
  </SpecRow>

  <SpecRow tags={['plugin', 'worker']} title="Extend with your own tasks and workers" href="/fleans/guides/custom-worker-host/">
    Wrap REST calls, queues, or any custom integration as a BPMN task by shipping a worker silo from a GitHub template. Engine and plugin hosts scale independently, so one workflow can fan out across your own fleet.

    <Fragment slot="note">Start from the custom-worker template on GitHub.</Fragment>
  </SpecRow>
</Section>
