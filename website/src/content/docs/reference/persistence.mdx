Fleans supports two persistence providers: **SQLite** (default, for local development) and **PostgreSQL** (for production and load testing). The provider is selected at startup via configuration — no code changes are required to switch.

## Provider Selection

Set `Persistence__Provider` (case-insensitive: `Sqlite` or `Postgres`) on every `fleans-*` workload via your deployment tool. For PostgreSQL, also provide a connection string via `ConnectionStrings__fleans`. The runtime key is documented in [Configuration / Persistence](/fleans/reference/configuration/#persistence).

<TabItem label="Compose bundle">

The release pipeline publishes the compose bundle with PostgreSQL as the provider (`fleans-postgres` ships in the bundle). To switch to SQLite (single-host debug), or to point at an external Postgres, drop a `docker-compose.override.yaml` next to the bundle's `docker-compose.yaml`:

```yaml
services:
  fleans-core:
    environment:
      Persistence__Provider: Postgres
      ConnectionStrings__fleans: "Host=my-external-pg;Database=fleans;Username=fleans;Password=secret"
  fleans-management:
    environment:
      Persistence__Provider: Postgres
      ConnectionStrings__fleans: "Host=my-external-pg;Database=fleans;Username=fleans;Password=secret"
  fleans-mcp:
    environment:
      Persistence__Provider: Postgres
      ConnectionStrings__fleans: "Host=my-external-pg;Database=fleans;Username=fleans;Password=secret"
  fleans-worker:
    environment:
      Persistence__Provider: Postgres
      ConnectionStrings__fleans: "Host=my-external-pg;Database=fleans;Username=fleans;Password=secret"
```

`docker compose up -d` from the bundle directory merges the override automatically. The override file is not regenerated by the post-processor, so it persists across `aspire publish` re-runs.

</TabItem>
<TabItem label="Helm">

```bash
# SQLite (chart default — single-host debug)
helm install fleans nightbaker/fleans

# Bundled PostgreSQL (chart provisions a containerised Postgres + secret)
helm install fleans nightbaker/fleans \
  --set persistence.provider=Postgres
```

The chart emits `Persistence__Provider` unconditionally. When `persistence.provider=Postgres` AND `postgres.enabled=true` (the default), `ConnectionStrings__fleans` is injected from the chart-managed secret. When `postgres.enabled=false`, the chart skips that injection so you can supply the connection string yourself via `extraEnv` — see below.

**External PostgreSQL (managed RDS, Cloud SQL, …):**

```yaml
# values-external-pg.yaml
postgres:
  enabled: false
persistence:
  provider: Postgres
extraEnv:
  - name: ConnectionStrings__fleans
    valueFrom:
      secretKeyRef:
        name: my-external-pg-secret
        key: connection-string
```

```bash
kubectl create secret generic my-external-pg-secret \
  --from-literal=connection-string='Host=my-external-pg.example.com;Port=5432;Database=fleans;Username=fleans;Password=...'
helm install fleans nightbaker/fleans -f values-external-pg.yaml
```

`extraEnv` accepts either `value: "..."` (literal — convenient for `--set` one-liners) or `valueFrom.secretKeyRef` (GitOps-friendly — recommended for production credentials). Both shapes propagate to every fleans-* workload via the chart's `commonEnv` helper.

### Manual / non-Compose / non-Helm hosts

If you're running silos outside Compose or Helm (bare-VM systemd units, ECS task definitions, hand-crafted Kubernetes manifests), set the same runtime keys directly. Either via `appsettings.json`:

```json
{
  "Persistence": { "Provider": "Postgres" },
  "ConnectionStrings": {
    "fleans": "Host=postgres;Database=fleans;Username=fleans;Password=secret"
  }
}
```

Or via environment variables (.NET configuration precedence puts env above `appsettings.json`):

```bash
Persistence__Provider=Postgres
ConnectionStrings__fleans="Host=postgres;Database=fleans;Username=fleans;Password=secret"
```

Accepted values for `Persistence__Provider` (case-insensitive): `Sqlite`, `Postgres`. Default: `Sqlite`.

## SQLite (default)

SQLite requires no extra configuration for local development. The default connection string points to a temp-directory database.

| Configuration Key | Description | Default |
|---|---|---|
| `ConnectionStrings:fleans` | SQLite connection string | `DataSource=fleans-dev.db` |
| `ConnectionStrings:fleans-query` | Optional read-side connection string | Same as primary |

**Startup behaviour:** SQLite uses `EnsureCreated()` — schema is created from the EF Core model on first run. There is no migration runner for SQLite.

## PostgreSQL

PostgreSQL requires an accessible Postgres instance and a connection string.

| Configuration Key | Description | Required |
|---|---|---|
| `ConnectionStrings:fleans` | Primary PostgreSQL connection string | Yes |
| `ConnectionStrings:fleans-query` | Read-replica connection string | No |

Example `appsettings.json`:

```json
{
  "Persistence": {
    "Provider": "Postgres"
  },
  "ConnectionStrings": {
    "fleans": "Host=localhost;Database=fleans;Username=fleans;Password=secret"
  }
}
```

**Startup behaviour:** PostgreSQL uses `MigrateAsync()` — EF Core migrations are applied automatically on `Fleans.Api` startup. `Fleans.Web` and `Fleans.Mcp` share the same database but do not run migrations.

**Behind PgBouncer:** Fleans works through PgBouncer in **transaction** pooling mode — the startup migrations serialize with a transaction-scoped advisory lock, which a transaction pooler keeps on one server connection. Two connection-string settings are worth adding there and without a pooler alike:

- `Maximum Pool Size=<n>` — every process opens one Npgsql pool per connection string (`fleans`, `fleans-query`, `fleans-journal`) of up to 100 connections by default. Size *processes × pools × n* below the server's (or pooler's) `max_connections`.
- `No Reset On Close=true` — Npgsql otherwise sends `DISCARD ALL` whenever a pooled connection is reused; under load that was ~7 extra server transactions per workflow instance on the read model. Fleans keeps no session state on pooled connections, so the reset buys nothing.

### Read replica

Point `ConnectionStrings:fleans-query` at a read replica of the `fleans` database (for example a PostgreSQL streaming-replication standby) and every read-model query moves there: the admin UI's lists and finished-instance views, the MCP tools, and the REST listings and state endpoint. Writes — grain state, the projector's read-model writes, migrations and health checks — stay on `ConnectionStrings:fleans`, so every process still needs it. Set the same value on every silo and on Fleans.Web and Fleans.Mcp. Unset, reads use the primary.

What to expect:

- **Lists lag a little more.** The read model already trails each instance by a moment (the projector builds it from the event log); replication lag adds to that. Each list row carries the event-log version it reflects (`stateVersion`).
- **Instance state never goes back in time.** A running instance is answered by its grain. A finished one is answered from the replica only once its row there says finished; until then the grain answers.
- The chart and the compose bundle provision only the primary; provision the replica yourself and pass the connection string (Helm: `extraEnv`).

## Separate journal database

Every workflow instance is event-sourced: its **journal** (the `WorkflowEventBatches` table) is the source of truth, and its **snapshots** (`WorkflowSnapshots`) are a cache over it. Under load the journal takes most of the writes. It can run on a database of its own — for example a sharded one — while the read model, the admin UI's queries and the other grain state stay on `fleans`.

| Configuration Key | Description | Default |
|---|---|---|
| `Persistence:Journal:Provider` | `Postgres`, `Citus` or `Sqlite` | `Postgres`; on a SQLite main database without `fleans-journal`, `Sqlite` (local dev) |
| `Persistence:Journal:Citus:ShardCount` | Shards per journal table on Citus (1–64000) | `128` |
| `ConnectionStrings:fleans-journal` | The journal's database | The `fleans` database |

With neither set, nothing changes: the journal tables live in the main database. The journal has its own EF Core migrations (history table `__EFJournalMigrationsHistory`), applied at startup to whichever database it uses, so a journal database holds only the two journal tables.

```bash
# The journal on its own PostgreSQL server
Persistence__Provider=Postgres
ConnectionStrings__fleans="Host=postgres;Database=fleans;Username=fleans;Password=secret"
ConnectionStrings__fleans-journal="Host=journal-db;Database=fleans_journal;Username=fleans;Password=secret"
```

Both tables are read and written **by workflow instance id only** — no joins, no queries across instances — and instance ids are random (Guid v4). That is what lets a distributed database shard them.

### Citus

With `Persistence:Journal:Provider=Citus`, startup applies the journal migrations and then distributes both tables by `InstanceId` into `Persistence:Journal:Citus:ShardCount` shards (default 128), snapshots colocated with their journal (`create_distributed_table`). Every journal command then goes to a single shard with plain PostgreSQL semantics. Tables that are already distributed are left alone, so every silo can run it — and a changed shard count does not reshard them: choose it with headroom before the first start.

```bash
Persistence__Provider=Postgres
Persistence__Journal__Provider=Citus
ConnectionStrings__fleans="Host=postgres;Database=fleans;Username=fleans;Password=secret"
ConnectionStrings__fleans-journal="Host=citus-coordinator;Database=fleans_journal;Username=fleans;Password=secret"
```

- Install the extension in the journal database first (`CREATE EXTENSION citus;`) and add your worker nodes; startup fails with a clear message otherwise.
- Start from a fresh journal database: the tables are distributed right after they are created, while still empty.
- Without `ConnectionStrings:fleans-journal`, `Citus` distributes the journal tables inside the `fleans` database, which then has to be a Citus coordinator; the other tables stay local to it.
- Citus is AGPL-3.0. Running it unmodified is fine; review the licence before you modify or redistribute it.

**YugabyteDB** (YSQL speaks the PostgreSQL protocol) is the alternative when built-in Raft failover matters more than the smallest change. It is not a supported provider yet: it needs retries on snapshot-isolation conflicts and squashed migrations.

## Retention: purging finished instances

Fleans keeps every finished instance until you delete it: its event journal, its snapshot, and its rows in the read model. A typical 10-step instance stores about 15 KB, so a million finished instances is about 15 GB, and list queries scan ever-larger tables.

To delete old instances, call [`POST /Instances/purge`](/fleans/reference/api/#purge-endpoint) with a cutoff. It deletes instances that finished (completed, cancelled or failed) before `CompletedBefore`. Running instances are never deleted. A call-activity child is kept while its parent is still running.

Fleans does not run the purge on a schedule. Run it from a cron job, a Kubernetes `CronJob`, or by hand. Repeat each run until the response says `"hasMore": false`:

```bash
CUTOFF=$(date -u -d '90 days ago' +%Y-%m-%dT%H:%M:%SZ)
while :; do
  RESP=$(curl -sf -X POST "$FLEANS_API/Instances/purge" \
    -H 'Content-Type: application/json' \
    -H "Authorization: Bearer $TOKEN" \
    -d "{\"CompletedBefore\":\"$CUTOFF\"}") || exit 1
  echo "$RESP"
  echo "$RESP" | grep -q '"hasMore":true' || break
done
```

Things to know:

- **It cannot be undone.** Back up the database first if you need the history, for example for audits.
- **The cutoff must be at least 1 hour old.** A recently finished instance may still be loaded in a silo's memory. Purging it would let that copy write again later.
- **A purged id reads as "not found".** `GET /Instances/{id}/state` returns `404`.
- **Disk space.** PostgreSQL reuses the freed space after `VACUUM` (autovacuum does this). An SQLite file does not shrink until you run `VACUUM`.
- **The first purge of a large database** is best run off-peak, with a smaller `BatchSize` such as `200`.
- **Logs:** EventIds 14100 (purge started), 14101 (batch purged) and 14102 (purge finished).
- **Separate journal database:** the purge deletes the journal and snapshots by instance id in the journal's database, and the read-model rows in `fleans`.
