Tasks are the atomic units of work in a Fleans workflow. Each task maps to a `<bpmn:*Task>` element
and runs exactly once per activation. Fleans supports four task variants; Send, Receive, Manual and
Business Rule tasks are not implemented — see [Unsupported task types](#unsupported-task-types) below.

See also: [BPMN Support matrix](/fleans/concepts/bpmn-support/) for the full coverage table.

## Plain Task

A **Plain Task** (`<bpmn:task>`) has no executor: the token **waits** on it until something calls
`POST /Execution/complete-activity` with the instance id and the task's `ActivityId` — the same
external-completion pattern as a [service task without a type](/fleans/guides/service-tasks/). Use it
for work done outside the engine that a system reports back over REST.

**BPMN:**
```xml
<bpmn:task id="Task_1" name="Do something" />
```

A Plain Task blocks the workflow until it is completed. If you need a placeholder step that just
passes the token on, use a script task with an empty `<bpmn:script>` (or a trivial assignment)
instead.

## Script Task

A **Script Task** (`<bpmn:scriptTask scriptFormat="csharp">`) executes a C# expression via
[DynamicExpresso](https://github.com/dynamicexpresso/DynamicExpresso). The script is read from the
`<bpmn:script>` child element (a script inside `<extensionElements>`, such as `<camunda:script>`, is
ignored) and evaluated against a `_context` variable bag that exposes the current workflow variables.
C# (`scriptFormat` `csharp`, `c#` or omitted) is built in. Any other format — such as
`javascript` — runs on an external worker plugin; see [Other script languages](#other-script-languages).

**BPMN:**
```xml
<bpmn:scriptTask id="Task_1" name="Compute total" scriptFormat="csharp">
  <bpmn:script>_context.total = _context.price * _context.qty</bpmn:script>
</bpmn:scriptTask>
```

### What a script can contain

:::tip[Script rules]
- A script is a list of **expressions separated by `;`**. Each one is compiled and run on its own,
  in order, with a single parameter: `_context`.
- Use assignments to `_context` fields and C# expressions: arithmetic, string concatenation,
  comparisons, the ternary `?:`, casts, and calls on .NET types such as `int.Parse(…)` or
  `new List<object> { 1, 2, 3 }`.
  ```
  _context.total = _context.price * _context.qty; _context.label = "order-" + _context.orderId
  ```
- **No statements**: no `if`, `throw`, `return`, loops, or `var` locals. A local could not survive
  to the next `;` anyway — keep intermediate values on `_context`. Use `cond ? a : b` instead of
  `if`.
- `${name}` placeholders are rewritten to `_context.name`; bare names are **not**, so write
  `_context.amount`, not `amount`.
- Every script is compiled when the process is deployed: a script that does not compile rejects
  the deploy (`400`) and names the script task.
- Any exception at run time (including a 10-second timeout) fails the activity with error code
  **`500`**. A script cannot choose another error code — see
  [Error Handling](/fleans/guides/error-handling/#how-an-activity-fails).
:::

### Other script languages

A script in any format other than C# runs **outside the engine**, on an external-task worker
registered for the task type `fleans.script.<format>` (the format in lower case; `js` means
`javascript` and `py` means `python`). A runaway, memory-hungry or malicious script cannot then
hurt the engine, and the worker scales and upgrades on its own.

| `scriptFormat` | Worker |
|---|---|
| `csharp`, `c#`, omitted | Built in |
| `javascript`, `js` | `Fleans.Plugins.JavaScript` from [fleans-plugins](https://github.com/nightBaker/fleans-plugins) — see [JavaScript script tasks](/fleans/guides/javascript-script-tasks/) |
| anything else | Any worker you write for `fleans.script.<format>` |

```xml
<bpmn:scriptTask id="Task_1" name="Compute total" scriptFormat="javascript">
  <bpmn:script><![CDATA[
    const total = _context.items.reduce((sum, i) => sum + i.price * i.qty, 0);
    _context.total = total;
    _context.label = `order-${_context.orderId}`;
  ]]></bpmn:script>
</bpmn:scriptTask>
```

- The worker receives the script and **every visible variable**, and sends back only the top-level
  variables the script changed; those merge into the scope, and the rest keep their type.
- `${…}` is not rewritten in these formats — in JavaScript it is template-literal syntax.
- The script is checked by the worker when it runs, not at deploy. A deploy with no worker
  connected for the format **succeeds with a warning**; the task waits until a worker connects.
- A script that throws fails the activity with code **`500`** and the script's message. A worker
  may also fail it with a BPMN error code, which an error boundary event catches.
- Each run is an external-task round trip (tens of milliseconds) rather than an in-process call.

## User Task

A **User Task** (`<bpmn:userTask>`) suspends the workflow and waits for a human to act. Fleans
exposes a claim → complete (or fail / cancel) lifecycle via REST and the admin UI.

**BPMN:**
```xml
<!-- Requires xmlns:camunda="http://camunda.org/schema/1.0/bpmn" on <bpmn:definitions> -->
<bpmn:userTask id="Task_1" name="Approve request"
               camunda:assignee="manager"
               camunda:candidateGroups="approvers" />
```

:::note
The parser reads the assignment from the `camunda:assignee`, `camunda:candidateUsers` and
`camunda:candidateGroups` attributes (comma-separated lists) — other shapes, such as an
`<extensionElements>` assignment element, are ignored and leave the task claimable by anyone. The
workflow is paused until a user claims the task with `POST /UserTasks/{activityInstanceId}/claim`
and completes it with `POST /UserTasks/{activityInstanceId}/complete`;
`POST /Execution/complete-activity` is rejected for user tasks. See [User Tasks](/fleans/guides/user-tasks/).
:::

## Service Task (Custom Task)

A **Service Task** (`<bpmn:serviceTask type="…">`) delegates execution to a handler
identified by the `type` attribute. It runs on a [worker connected over gRPC](/fleans/guides/custom-worker-host/) —
your own, or the ready-made plugins' image; the engine images bundle none —
and its result comes back through `<fleans:output>` bindings.

**BPMN:**
```xml
<!-- Requires xmlns:fleans="https://fleans.io/schema/bpmn/1.0" on <bpmn:definitions> -->
<bpmn:serviceTask id="Task_1" name="Call external API">
  <bpmn:extensionElements>
    <fleans:taskDefinition type="rest-call" />
    <fleans:ioMapping>
      <fleans:input source="=apiUrl"  target="url" />
      <fleans:output source="=__response.body" target="result" />
    </fleans:ioMapping>
  </bpmn:extensionElements>
</bpmn:serviceTask>
```

The `type` value must match the task type a worker registers — `rest-call` above is the REST Caller
plugin from [fleans-plugins](https://github.com/nightBaker/fleans-plugins). To learn more:

- [Custom Tasks](/fleans/concepts/custom-tasks/) — architecture, event flow, parameter mapping, and the ready-made plugins.
- [Input/Output Mapping](/fleans/concepts/activities/io-mapping/) — the `<fleans:ioMapping>` expression syntax, shared by every task type.
- [Hosting workers](/fleans/guides/custom-worker-host/) — run workers next to the engine.
- [Writing custom tasks](/fleans/guides/writing-custom-tasks/) — step-by-step authoring guide.

:::note[Camunda back-compat]
Files exported from Camunda Zeebe (e.g. `<extensionElements><zeebe:taskDefinition type="..."/></extensionElements>`)
are accepted as-is — the BPMN converter understands both `<fleans:taskDefinition>` and the
legacy `<zeebe:taskDefinition>` shape. New Fleans-authored files should use the `<fleans:...>`
namespace (`xmlns:fleans="https://fleans.io/schema/bpmn/1.0"`).
:::

A `<bpmn:serviceTask>` with no `type` attribute and no `taskDefinition` is not dispatched anywhere:
it waits for `POST /Execution/complete-activity`, like a plain task — see
[Service Tasks](/fleans/guides/service-tasks/).

## Input/output mapping

Every task type accepts `<fleans:ioMapping>`: inputs compute task-local variables from C#
expressions before the task runs, and outputs pick what it hands back to the process. See
[Input/Output Mapping](/fleans/concepts/activities/io-mapping/).

## Unsupported task types

Send Task (`<bpmn:sendTask>`), Receive Task (`<bpmn:receiveTask>`), Manual Task
(`<bpmn:manualTask>`) and Business Rule Task (`<bpmn:businessRuleTask>`) are **not implemented**.
The converter does not recognise them: the element is skipped and every sequence flow to or from it
is dropped, so the process **deploys without an error but with a gap** — a token that should reach
the element stops where the dropped flow started. Model the step with a supported task instead (for
example a service task for a send, or a message intermediate catch event for a receive).
