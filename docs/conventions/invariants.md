# Load-bearing invariants

These guard correctness. Break them and silent bugs ship. `CLAUDE.md` carries a one-line summary of each; this file is the full rule set — read it before touching activity lifecycle, compensation, effect handlers, user-task claims, or anything reachable from a stream handler.

## Each activity instance executes at most once

Every non-boundary activity instance runs exactly once (completes OR fails). An activity definition can be visited multiple times (e.g., in a loop), creating a new instance each time. `TimerCallbackGrain` keys on `hostActivityInstanceId` to distinguish.

A script task's *script* may run more than once — the instance re-dispatches it when no result arrives within `Fleans:Worker:ScriptResultTimeout`, and on activation (see [Script dispatch](#script-dispatch-and-in-process-conditions)) — but only its first result is applied: guards 1–2 below drop the rest. Scripts only transform variables, so a repeated run has no side effect.

## Script dispatch and in-process conditions

Conditions — gateway flows (`EvaluateConditionEvent`), complex-gateway activation (`EvaluateActivationConditionEvent`), multi-instance completion (`EvaluateCompletionConditionEvent`) and conditional-event watchers — are evaluated **inside the workflow instance**, in the turn that needs them, with the silo's `IConditionExpressionEvaluator`. The aggregate still emits them as `PublishDomainEventEffect`s; `WorkflowInstance.PerformEffects` takes them out and queues them, and `RunExecutionLoop` evaluates the queue once no activity is pending — exactly what the stream handler used to do in a later turn:

- A result is resolved (`ResolveExternalCompletions`) only when it changed state, and only for the completions it caused: the turn's own completions are passed as `alreadyTransitioned` (guard 9). A false activation or completion condition resolves nothing — otherwise every evaluation would re-run `HandleScopeCompletions`, which queues the next completion-condition evaluation, forever.
- An evaluation for a gateway that is no longer active (an exclusive gateway took an earlier flow, a boundary cancelled it) is skipped (1160). An evaluation error fails the activity (1161); a completion-condition error is log-only (1162), as before.

Script tasks are **dispatched, not published**: `RunExecutionLoop` collects the `ExecuteScriptEvent`, and `ProcessPendingEvents` sends it after its final journal append, one-way (`[OneWay] IScriptExecutorGrain.Run`), with the merged variables. The executor calls back `CompleteActivity` / `FailActivity`, retrying transient failures (`OrleansException`, incl. `WorkflowInstanceStaleException`, and `TimeoutException`) five times; a result the instance rejects for another reason (variables over the size limit) fails the activity instead. Recovery of a lost dispatch or result is the instance's job:

- **Result timeout.** Each dispatch is tracked in memory; a grain timer (every half `ScriptResultTimeout`) re-dispatches a script still executing past its due time (1165), and fails it with a `TimeoutException` after `WorkerEvaluatorOptions.ScriptDispatchAttempts` (3) dispatches (1166).
- **Activation.** `OnActivateAsync` re-dispatches every script task the journal shows as executing (1167): the previous activation may have died with its in-memory tracking.
- **Not covered:** an instance whose activation and every callback are lost (e.g. the whole cluster restarts while a script runs) resumes the script only when something activates it again — nothing does so on its own. A durable sweep (a reminder per waiting instance) would close it; not done, since it costs a storage write per script.

**When adding a new kind of in-process evaluation or dispatched work: queue it in the turn, apply it like its former callback (stale guard first), and give lost work a recovery path that does not depend on the activation surviving.**

## Compensation handlers run in isolated child scopes

Each handler gets a fresh variable scope seeded with the compensable activity's completion-time snapshot, overlaying the enclosing scope. After a handler completes successfully, its variable changes MUST be merged back into the enclosing scope before the next handler spawns. Otherwise: (a) later handlers see stale variables, and (b) compensation side-effects vanish after the walk finishes. Enforced via `WorkflowExecution.AdvanceCompensationWalkIfHandlerCompleted` emitting a `VariablesMerged` event targeting the parent scope's variables ID.

## Registration-vs-cleanup error asymmetry

Registration-path failures (build-time `ProcessRegisterMessage`, handler-time `RegisterTimerEffect.Activate`, `SubscribeMessageEffect` / `SubscribeSignalEffect`, `RegisterUserTaskEffect`) MUST route to `FailActivity` so the workflow surfaces the failure. User-task registration makes at most three attempts with 100 ms / 200 ms backoff; after exhaustion, `ProcessFailureEffects` handles the exact activity instance, including its BPMN error boundary if present (#851).

Cleanup-path failures (`UnsubscribeMessageEffect`, `UnsubscribeSignalEffect`, `UnregisterTimerEffect`, `ThrowSignalEffect`) MUST be log-only — the owning activity has already completed or been cancelled, and failing now would violate the "at most once" invariant.

Effect handlers in `Fleans.Application/Effects/{Message,Signal,Timer,UserTask}EffectHandler.cs` enforce this. User-task completion/claim persistence failures remain log-only; they must not fail an activity that already changed state.

## User-task claim authorization is a three-rule OR

`UserTaskGrain.Register` is idempotent by activity instance id: once a record exists, registration is a no-op. This makes a retry after a lost reply safe and preserves the original creation time, claim and completion state. A failed first write must still be retried — mutated in-memory state alone does not mean the record exists (#851).

`UserTaskLifecycle.Claim` allows a claim iff at least one of:

- (a) `Assignee == userId`
- (b) `CandidateUsers.Contains(userId)`
- (c) `CandidateGroups ∩ userGroups ≠ ∅` (ordinal case-sensitive)

When no constraint is present the task is unrestricted.

Caller-side `userGroups` comes from `IUserGroupResolver` — `JwtUserGroupResolver` reads `HttpContext.User.FindAll("groups")` when `Authentication:Authority` is configured; `BodyUserGroupResolver` reads the body when auth is disabled (body-supplied groups are ignored under JWT so callers can't spoof). The acting `userId` follows the same split via `IUserIdResolver` (#793): under JWT it comes from the `Authentication:UserIdClaim` claim and a differing body `UserId` is a 403.

Rejection messages MUST stay identifier-free; structured audit lives in `LogUserTaskClaimRejected` (EventId 1066, Warning) carrying `UserGroupCount` only — never group names.

**When extending (e.g., role-based claims): add a 4th branch, keeping the existing three.**

## Journal tables are accessed by `InstanceId` only

The journal (`WorkflowEventBatches`) and snapshots (`WorkflowSnapshots`) may live in a database of their own, and on Citus they are distributed by `InstanceId` (#879). Two rules keep that possible:

- **Every command on them filters or keys by `InstanceId`** — no joins, no query across instances (no scans by date, status or definition). Only `EfCoreEventStore` touches `FleanJournalDbContext`; `EfCoreEventStoreTests.EveryJournalCommand_IsKeyedByInstanceId` fails on a command that is not keyed. Anything that needs to find instances (lists, retention, cleanup) selects them from the read model, then reaches the journal by id.
- **`InstanceId` stays a random Guid v4** (`Guid.NewGuid()`), never a time-ordered id (v7, sequential): a monotonic key would put every new instance on the last shard under range sharding. People find instances by `BusinessId`.

**When adding journal access: key it by `InstanceId`, or it does not belong on the journal.**

## Start-event subscriber caches are hints; the definition grain decides

Message, signal and conditional starts take the subscribed processes from the host's `StartEventSubscriptionCache` (#858), so no grain per event name is on the start path. The listener and registry grains (`IMessageStartEventListenerGrain`, `ISignalStartEventListenerGrain`, `IConditionalStartEventRegistryGrain`) stay the persisted registrations and are read only on a cache miss. Two rules keep a stale entry harmless:

- **Every start still asks `IProcessDefinitionGrain.GetStartableDefinition`** and resolves the start activity — and, for a conditional start, the condition — from the definition it returns, never from the cache (`StartEventLauncher`). A disabled process or a version that dropped the start event therefore starts nothing even from a stale entry; only a *newly* subscribed process can be missed.
- **Every registration change notifies the hosts.** `ProcessDefinitionGrain` calls `IStartEventSubscriptionNotifierGrain.NotifyChanged()` after deploy, enable and disable — in a `finally`, so registrations written before a failing one still reach the hosts; it returns once every subscribed host has dropped its entries (5 s timeout per host). Staleness when a host misses it: at most `StartEventSubscriptionCache.EntryLifetime` (30 s), after which every entry reloads; a host that the notifier dropped or forgot (reactivation) clears at its next renewal (every minute while in use). A notify failure is log-only (6006): the registrations are already persisted.
- **The cache subscribes off the caller's context.** Its first lookup can come from inside a grain (`MessageDeduplicationGrain`, #743), and Orleans refuses to create an observer reference there, so the renewal runs under `Task.Run`. A renewal made inside a grain would fail (9386) and leave that host's cache stale for `EntryLifetime`.

**When adding a path that changes start-event registrations, call `NotifyChanged` after it; when adding a start path, take everything but the process keys from `GetStartableDefinition`.**

## A message sent with an idempotency key happens once

`POST /Execution/message` without `IdempotencyKey` is not safe to retry: the start-event fallthrough mints new instance ids on every call. With a key, `WorkflowCommandService.SendMessage` hands the whole send — correlate, else start — to `IMessageDeduplicationGrain`, keyed by message name + the escaped key (`MessageDeduplicationKey`, the `MessageCorrelationKey` format and 1024-character limit) (#743). Rules that keep it exactly-once:

- **The grain is not reentrant.** Sends of one key run one at a time; a repeat finds the record and returns it (14400). Keep it non-reentrant: nothing on the send path calls back into it.
- **Plan before start.** For a start, the grain asks `StartEventLauncher.PlanMessageStarts` for one random-v4 instance id per subscribed process, persists the plan (`Starting`), then `StartPlanned` starts them and the outcome is persisted (`Started`). A send interrupted between the two writes is resumed by the next repeat with the same plan (14404) — a repeated `StartWorkflow` of a started instance is a no-op (guard 11 below). Never mint an id after the plan is written.
- **A correlated delivery is recorded too** (`Correlated`), so a retry after the subscription was consumed does not fall through to a message start event. Not covered: a crash between the delivery and that write.
- **Nothing delivered, nothing recorded.** No subscribed process, or every planned start skipped or failed, leaves no record, so a later retry is a fresh send.
- **The first send wins and counts for `MessageDeduplicationState.Window` (24 h).** A repeat with other variables gets the first outcome. An expired record is replaced by the next send; rows are not purged yet.
- **Signals are not deduplicated** — a broadcast has no identity; callers who need a once-only start use a message start event with a key.

## Stream-redelivery idempotency

Every state-mutating grain method reachable from an `[ImplicitStreamSubscription]` handler MUST be idempotent under at-least-once delivery. Silent doubling under redelivery is a production correctness bug, not a test flake.

Current guarantees are a layered guard set:

1. Grain-entry stale guard `HasActiveEntry(activityInstanceId)` on `CompleteActivity`/`FailActivity` (both `FailActivity` overloads, with and without variables — the variables are merged only after the guard).
2. Domain-entry stale guard `entry.IsCompleted` as defense-in-depth.
3. `joinState.HasFired` on `ApplyActivationConditionResult` (a complex gateway's activation condition, now evaluated in the instance).
4. `entry.IsCompleted || entry.ActivityInstanceId != hostActivityInstanceId` on `CompleteMultiInstanceEarly`.
5. `CompleteConditionSequence` relies on set-by-key projection idempotency; its in-process caller also skips a gateway that is no longer active.
6. `WorkflowExecution.IsTimerFireStale(timerActivityId, hostActivityInstanceId)` pre-call check on `HandleTimerFired` — mirrors the aggregate's internal regular-timer and ESP-scope-container guards; late reminder fires (post-completion, post-cancel) are logged as warnings (EventId 3034) and silently dropped. Pairs with `TimerCallbackGrain.Cancel`'s swallow-on-failure cleanup per the registration-vs-cleanup asymmetry rule.
7. **Pending-external-event op-id ledger** (`State.PendingOperations` / `State.AppliedOperations`, #657) — the three caller-retried sibling-grain RPCs (`OnChildWorkflowCompleted`/`OnChildWorkflowFailed`/`OnChildEscalationRaised`) take a deterministic op-id and dedup on it: applied → return persisted outcome; in-flight → await existing in-memory TCS; fresh → durably enqueue via `RaiseEvent(PendingEventEnqueued)`. The queue is persisted (survives forced deactivation; rebuilt with fresh TCSes in `OnActivateAsync`), and the drain path emits `PendingEventDrained` (+ `PendingEventApplied` for retried ops). `AppliedOperations` is GC'd on terminal state (guard 2's `IsCompleted` covers post-completion retries). The signal path is never retried, so it persists with a fresh-Guid key and no dedup. Caller side: `IGrainFactory.CallWithRetry`; the op-id *string* format lives in the application layer (the domain effect carries only a raw `EscalationInstanceId` Guid).
8. **Pre-execution activity check** (a read, not a lock) `IWorkflowInstanceCallback.GetVariablesIfActive(activityInstanceId, variablesId)` in `CustomTaskHandlerBase.HandleAsync` (called from `OnNextAsync`, which then deactivates the handler, #922) — runs *before* the plugin's `ExecuteAsync` and returns `null` once the activity instance has completed or failed, so a redelivered/duplicate `ExecuteCustomTaskEvent` is logged (EventId 4038) and skipped instead of re-running plugin side effects. Guards 1–2 only absorb the duplicate *completion*; this one prevents the duplicate *execution* of a finished activity. Error split in the handler: transient grain-call failures (`TimeoutException`, `OrleansException`) of the check or of `CompleteActivity` are rethrown for stream redelivery (EventId 4039) — never `FailActivity`, since the plugin either has not run or already succeeded; any other exception (deterministic, e.g. unknown variable scope) goes to `FailActivity`. **Scope: custom tasks only** — a re-dispatched script re-executes and relies on guards 1–2 to drop the duplicate result; conditions are evaluated in the instance and never redelivered. **Not covered** (the plugin runs again; plugins need an idempotency key): a run interrupted mid-`ExecuteAsync` (worker crash, activation deactivation), a transient `CompleteActivity` failure after the plugin succeeded, and two concurrent handler activations during a membership change (both read "active" before either completes — closing that needs a durable claim on the workflow instance, #818). Regression tests: `CustomTaskRedeliveryTests` (redelivery after completion and after failure, deterministic check error fails the activity, multi-silo test with queued duplicates).

9. **Each queued callback transitions only its own completions** (#837). `ResolveExternalCompletions` transitions the `ActivityCompleted` events in the uncommitted buffer, and when `ProcessPendingEvents` runs a queued `[AlwaysInterleave]` callback (child completed/failed/escalation, signal delivery, boundary signal) at the end of a turn, that buffer can still hold the turn's own completions — already transitioned by `RunExecutionLoop`. It records their ids before calling the aggregate and passes them as `alreadyTransitioned`, so their successors are not spawned a second time. By id, not by buffer position: an effect's `PersistStateAsync` drains the buffer mid-callback.
10. **A re-read keeps the live state, or retires the activation** (#845). When an append fails or conflicts, Orleans' `CustomStorage` adaptor re-reads through `ReadStateFromStorage`, swaps `State` for the object returned, and retries the batch on it. The live `State` already holds that batch (the aggregate applies before `RaiseEvent`), so when nothing was stored past `_journalVersion` the grain returns it unchanged (1138, Warning) and the call carries on. It does the same when the failed try threw and the journal moved, since the try may have been stored after all: the retry resends it with the same batch id at the same version and the store confirms it instead of appending it twice (1139, Warning, #877). When the journal moved on because of another writer (the append returned `false`), the aggregate is out of date: the grain marks itself reloaded (1137, Error), calls `DeactivateOnIdle`, skips the projector notification and the snapshot write from the re-read `State`, and rejects new calls and further drains with `WorkflowInstanceStaleException` before applying anything. It is an `OrleansException`, so `CallWithRetry`, the custom-task handler, the script executor's callback and stream redelivery retry it; the signal/message subscribe effects let it through instead of failing the activity; REST maps it to 503. The next activation replays the journal and catches the read model up.
11. **One start call, idempotent by definition** (#863). `IWorkflowInstanceGrain.StartWorkflow(definition, startActivityId, businessId, variables, parent)` is the only way to create an instance: it journals `WorkflowStarted`, the start activity, `ParentInfoSet`, `VariablesMerged` and `ExecutionStarted` as one batch, so an instance is either absent or started. A repeated call for an instance already started from the same `ProcessDefinitionId` is a no-op (1147); a different definition throws. Every caller first asks `IProcessDefinitionGrain.GetStartableDefinition`, the single process-disabled check (`null` = disabled): the API answers 409, message/signal/conditional/timer start events skip, a call activity fails. No effect may rely on the instance's read-model row existing: the projector writes it asynchronously (#861), so no other table has a foreign key to `WorkflowInstances`.
12. **The read-model projector writes only forward** (#861). `WorkflowInstanceProjector` handles `InstanceAdvanced(InstanceId, Version)` by replaying the journal to its head and writing the projection at that version. A notification at or below the version it last projected is skipped in memory (redeliveries and the bursts that queued behind one projection); after a reactivation, the write itself is guarded: each `WorkflowInstances` row stores `ProjectedVersion`, and a write lands only past it, so a late, repeated or stale-activation write never rolls the row back. It never mutates grain state, and a failed projection is rethrown for redelivery. Writes go through the silo's `ProjectionBatcher`: a notification is acknowledged only once the batch carrying its write is durable, a failed batch fails every write in it, and a batch holding two projections of one instance keeps the newer. Regression tests: `EventSourcingIntegrationTests.Projection_RedeliveredNotification_IsSkipped`, `EfCoreWorkflowStateProjectionTests.Write_OlderVersion_DoesNotRollTheRowBack`, `EfCoreWorkflowStateProjectionTests.WriteBatch_OlderAndNewerOfOneInstance_KeepsTheNewer`, `EventSourcingIntegrationTests.ReadModel_FailedBatch_EveryInstanceInItIsRedeliveredUntilItLands`.
13. **Signal bucket subscribe/unsubscribe are set-by-key** (#859). `SignalCorrelationGrain.Subscribe` ignores a key `(WorkflowInstanceId, ActivityId)` it already holds and `Unsubscribe` of an absent key is a no-op, so a redelivered `SubscribeSignalEffect` / `UnsubscribeSignalEffect` changes nothing. Both reach the same bucket on every delivery because the bucket is a stable hash of the instance id (`SignalCorrelationOptions.BucketFor`). A broadcast takes the bucket's subscriptions before delivering, so a broadcast retried by its caller does not deliver twice; a transient delivery failure puts the subscription back for the next broadcast (#742), never re-delivers within the same one. Regression tests: `SignalBucketTests`.

11. **One start call, idempotent by definition** (#863). `IWorkflowInstanceGrain.StartWorkflow(definition, startActivityId, businessId, variables, parent)` is the only way to create an instance: it journals `WorkflowStarted`, the start activity, `ParentInfoSet`, `VariablesMerged` and `ExecutionStarted` as one batch, so an instance is either absent or started. A repeated call for an instance already started from the same `ProcessDefinitionId` is a no-op (1147); a different definition throws. Every caller first asks `IProcessDefinitionGrain.GetStartableDefinition`, the single process-disabled check (`null` = disabled): the API answers 409, message/signal/conditional/timer start events skip, a call activity fails. Because the start runs in the same turn, the instance's read-model row does not exist until that turn's first append: an effect that writes a row referencing it (user-task registration — `UserTasks` has a foreign key to `WorkflowInstances`) calls `IEffectContext.EnsureInstancePersistedAsync()` first, which appends only while the journal is still empty.

**When adding a new state-mutating method on `IWorkflowInstanceCallback` (or any other interface called from a stream handler), extend this guard set or prove the new path is naturally idempotent.**
