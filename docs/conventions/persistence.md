# Persistence providers

Two providers: **SQLite** (default, local dev) and **PostgreSQL** (production / load testing). Selected via configuration — no code changes needed.

## Configuration

- **Config key:** `Persistence:Provider` (values: `Sqlite` | `Postgres`, case-insensitive, default `Sqlite`). `AddFleansPersistence` throws `ArgumentException` on any other value (typos, empty, whitespace) so misconfigured deployments fail fast — mirrors the validation pattern in `FleanStreamingExtensions.cs:26`.
- **Aspire:** set `FLEANS_PERSISTENCE_PROVIDER=Postgres` before launch to auto-provision a Postgres container.
- **Connection strings:** SQLite uses `FLEANS_SQLITE_CONNECTION` / `FLEANS_QUERY_CONNECTION`. PostgreSQL uses `ConnectionStrings:fleans` (required) and `ConnectionStrings:fleans-query` (optional read replica — see [Reads from a replica](#reads-from-a-replica-fleans-query)).
- **Journal store (#879):** `Persistence:Journal:Provider` (`Postgres` | `Citus` | `Sqlite`, empty = `Postgres`, or `Sqlite` on a SQLite main database without a journal connection), `Persistence:Journal:Citus:ShardCount` (default 128) and `ConnectionStrings:fleans-journal` (default = the main database) — see [Journal store](#journal-store-separate-database-citus).
- **Migration strategy:** SQLite uses `EnsureCreated()`. PostgreSQL uses `MigrateAsync()` (migrations applied automatically by `Fleans.Api` on startup).
- **Adding a column to an existing table:** generate a Postgres migration (`dotnet ef migrations add <Name> --project Fleans.Persistence.PostgreSql --context FleanCommandDbContext --output-dir Migrations/Command`; for the journal tables `--context FleanJournalDbContext --output-dir Migrations/Journal`). **Pre-1.0, skip the SQLite backfill** (`SqliteSchemaInitializer.AdditiveColumns`) — see the pre-1.0 rule in `CLAUDE.md`. `EnsureCreated()` is a no-op on an existing SQLite file, so after a schema change delete the stale dev DB (Aspire's `$TMPDIR/fleans-dev.db`, which E2E runs reuse) instead of hitting `no such column` at first query.
- **Migrations live per-provider:** `Fleans.Persistence.Sqlite/Migrations/Command/` and `Fleans.Persistence.PostgreSql/Migrations/Command/`. Command-context migrations are maintained (command and query share the same database), plus the journal context's in `Fleans.Persistence.PostgreSql/Migrations/Journal/` (history table `__EFJournalMigrationsHistory`).

## Reads from a replica (`fleans-query`)

Every read of the read model goes through `FleanQueryDbContext` (`NoTracking`, no write surface: `IFleanQueryContext` exposes `IQueryable<T>` only, and `WorkflowQueryService` / `PostgresUserTaskFilterStrategy` never call `SaveChanges` or `Execute*`). That is `IWorkflowQueryService` — the admin UI, MCP tools and REST listings/state all go through it — and nothing else reads with `FleanCommandDbContext` except writers: grain storage, `EfCoreProcessDefinitionRepository` (behind `ProcessDefinitionGrain`), the projection (`EfCoreWorkflowStateProjection` reads the row it is about to write and must see the primary) and the purge service (it deletes what it selects). So pointing the query context at a replica is configuration only:

- PostgreSQL: set `ConnectionStrings:fleans-query` to a streaming replica of the `fleans` database. `AddPostgresPersistence` gives it its own `NpgsqlDataSource` (keyed `fleans-query`); unset, the query context shares the primary's.
- SQLite: `FLEANS_QUERY_CONNECTION` (a separate file is not a replica — dev only).
- Replica lag adds to the projector's lag. The listings are eventually consistent either way; a *running* instance's state still comes from its grain, and a completed one is served from the replica only once its row there says completed (until then the grain answers), so the state endpoint never goes back in time.
- Only the read model moves: migrations (`EnsureDatabaseSchemaAsync`) and health checks use the command context, so every process still needs `ConnectionStrings:fleans`.

## Provider packages

`Fleans.Persistence.Sqlite` and `Fleans.Persistence.PostgreSql` — each registers a `RelationalModelCustomizer` subclass via `ReplaceService<IModelCustomizer>` for provider-specific model tweaks (e.g., SQLite stores `DateTimeOffset` as string; PostgreSQL uses native `timestamptz`).

## Adding a new provider

1. Create a new `Fleans.Persistence.<Provider>` project.
2. Implement a `<Provider>ModelCustomizer : RelationalModelCustomizer`.
3. Add an `Add<Provider>Persistence()` extension.
4. Generate initial migrations.
5. Wire into host `Program.cs` files.

## Postgres migration race across silos

Every silo (Api/Web/Mcp/Worker) calls `EnsureDatabaseSchemaAsync` at startup, which under Postgres calls `MigrateAsync`.

EF Core's per-migration lock is acquired only during `__EFMigrationsHistory` writes, not while running the migration SQL — so two silos that both observe a migration as pending can both try to `CREATE TABLE` and the loser fails with `relation "X" already exists`.

`EnsureDatabaseSchemaAsync` wraps `MigrateAsync` in a **transaction-scoped** `pg_advisory_xact_lock(8723547283)`, held in an open transaction on a connection of its own (`AcquireMigrationLockAsync`: a clone of the context's connection) until the migrations are done, to serialize concurrent migration attempts cleanly. Not a session-level lock (#923): through PgBouncer in transaction mode the lock, the migrations and the unlock each run on whatever server connection the pooler hands out, so the unlock misses and the lock leaks into the pool — the next silo waits forever. An open transaction keeps its server connection, and the lock ends with it even if the process dies. `EnsureDatabaseSchemaTests.ThroughPgBouncerInTransactionMode_…` runs three silos through a real PgBouncer. The lock key is arbitrary but must be the same across all silos. SQLite uses `EnsureCreatedIgnoreRaces` and is unaffected.

## Custom-task catalog persistence

`CustomTaskCatalogGrain` uses `IPersistentState<CustomTaskCatalogState>` keyed by `GrainStorageNames.CustomTaskCatalog`, backed by `EfCoreCustomTaskCatalogGrainStorage` and the `CustomTaskCatalogEntries` table (composite PK on `(TaskType, SiloName)`; `ParameterSchemaJson` stored as a JSON text column via `System.Text.Json`).

Test clusters must register memory grain storage for this name in `WorkflowTestBase` alongside the other registries.

## Deployment requests (#900)

`DeploymentRequestGrain` uses `IPersistentState<DeploymentRequestState>` keyed by `GrainStorageNames.DeploymentRequests`, backed by `EfCoreDeploymentRequestGrainStorage` and the `DeploymentRequests` table (one row per request, ETag-checked like `UserTasks`; `Approvals` and `ReviewerGroups` are JSON text columns; index on `(Status, RequestedAt)` for the review queue). The same table is the query side: `IWorkflowQueryService.GetDeploymentRequests` / `GetDeploymentRequest` read it through `FleanQueryDbContext`. `WorkflowTestBase` registers the production storage.

## Message deduplication (#743)

`MessageDeduplicationGrain` uses `IPersistentState<MessageDeduplicationState>` keyed by `GrainStorageNames.MessageDeduplications`, backed by `EfCoreMessageDeduplicationGrainStorage` and the `MessageDeduplications` table: one row per message name + idempotency key (primary key `Key`, at most 1024 characters, the escaped `MessageCorrelationKey` format), read and written by that key only, ETag-checked. `PlannedStarts` and `StartedInstanceIds` are JSON text columns; `ReceivedAt` is a native timestamp (a string on SQLite). Only sends with an idempotency key create a row — one or two writes each (plan, then outcome; a correlated delivery writes once). Retention: a record answers repeats for 24 h (`MessageDeduplicationState.Window`) and the next send of an expired key overwrites it; nothing deletes expired rows yet (pre-1.0). `WorkflowTestBase` registers the production storage, so reactivation tests read the row back.

## Signal subscriptions: buckets, per-row writes (#859)

A signal name's subscriptions are spread over **`Fleans:Signals:BucketCount` buckets** (default 64), one `SignalCorrelationGrain` each, keyed `(bucket, signalName)` (`IGrainWithIntegerCompoundKey`: integer key = bucket, key extension = name). A subscription lives in bucket `SignalCorrelationOptions.BucketFor(workflowInstanceId)` — FNV-1a over the Guid's bytes mod B, stable across processes (never `GetHashCode`), pinned by `SignalCorrelationOptionsTests`. Address buckets only through `SignalCorrelationGrainFactoryExtensions`: `GetSignalCorrelationGrain(name, instanceId, options)` for subscribe/unsubscribe, `BroadcastSignal(name, options)` to call all B buckets in parallel (a failed bucket is counted in `SignalBroadcastResult`, it does not stop the others). The bucket count is part of the stored key, so every process (silos, API, Web, MCP) must use the same value and it changes only on an empty cluster.

Tables: `SignalCorrelations` has one row per bucket, key `(SignalName, Bucket)`, holding the ETag; `SignalSubscriptions` rows are keyed `(SignalName, Bucket, WorkflowInstanceId, ActivityId)` and `SignalName` is the plain signal name (the Events page reads it unchanged). Inside a bucket, `EfCoreSignalCorrelationGrainStorage.WriteStateAsync` writes only what changed, so a subscribe or unsubscribe costs the same at 10 or 100,000 subscribers:

- **Change set on the state.** `SignalCorrelationState` is mutated only through `AddSubscription` / `RemoveSubscription` / `TakeAllSubscriptions` (`Subscriptions` is read-only). They record added subscriptions, removed keys and a "cleared" flag — fields that are `[NonSerialized]` and `Ignore`d in `FleanModelConfiguration`. The grain calls `AcceptChanges()` only after a successful `WriteStateAsync`; a failed write keeps the set, so the next write retries it.
- **One transaction per write.** Load the bucket's `SignalCorrelations` row alone (no `Include`) for the ETag check, then: the broadcast clear as one `ExecuteDelete` by `(SignalName, Bucket)`, each removed key as one `ExecuteDelete` by key, the added rows as inserts, and the new ETag. Deletes run before inserts, so a key removed and re-added in one change set is replaced.
- **First write** (no parent row) inserts the parent and every subscription in the state.
- Activation (`ReadStateAsync`) still loads all of the bucket's rows — once per activation, not per change.
- **Delivery failures (#742).** A broadcast takes the bucket's subscriptions (one set-based delete) before delivering. A subscriber whose delivery fails transiently (`TimeoutException`, `OrleansException` — including `WorkflowInstanceStaleException`) is added back afterwards and receives the next broadcast; the missed signal itself is not redelivered. Other failures stay dropped. A subscription re-added meanwhile (non-interrupting re-subscribe) wins. If the clear's write fails, nothing was delivered and the subscriptions go back into memory.

Any new mutation of the state must go through a domain method that records the change; a write the storage cannot see is silently lost. Pre-1.0 the bucketed schema (`SignalBuckets` migration) needs a fresh database: rows written before it are not moved into their buckets.

## Event store: journal, snapshots, read model

`WorkflowInstance` is event-sourced: the journal (`WorkflowEventBatches`) is the only source of truth. Snapshots and the read model derive from it. Design: [`docs/plans/2026-10-16-event-sourced-workflow-instance-design.md`](../plans/2026-10-16-event-sourced-workflow-instance-design.md).

- **Versions.** A grain's version is its event count. `IEventStore.AppendEventsAsync(instanceId, events, expectedVersion)` stores the batch as versions `expectedVersion + 1`, … — the store does the numbering, callers pass the count. `ReadEventsAsync(afterVersion)` returns `Version > afterVersion`.
- **One row per append (#867).** A `WorkflowEventBatches` row is one `ConfirmEvents` batch: `(InstanceId uuid, FirstVersion, LastVersion, BatchId uuid, Payload)`, keyed `(InstanceId, FirstVersion)`. That key is the concurrency check — two writers that both saw version *n* collide on `FirstVersion = n + 1`, whatever their batch lengths. Versions callers see (and snapshot versions) are always append boundaries, so `ReadEventsAsync` reads batches with `FirstVersion > afterVersion` and throws on a gap rather than replay a partial history. Per-event rows cost ~190 bytes of row and index overhead each, about half the journal; batching removes most of it.
- **Journal format: Orleans binary.** `Payload` is the batch as a `List<WorkflowEvent>` written by the Orleans serializer (the same one that carries events and state across grain calls and writes snapshots). Every event is `[GenerateSerializer]` with explicit `[property: Id(n)]` and a short `[Alias("ev.<Name>")]` — the alias is the type tag stored per event, so keep it short and never reuse one. Collections in events are `List<T>`. `JournalEventSerializationTests` round-trips every `WorkflowEvent` type; a new event without a codec fails there, not in production. Variable values keep their CLR types on replay (no JSON `int` → `long` drift). The payload is not readable with `SELECT`; decode it with the Orleans `Serializer` when debugging.
- **Variables are journaled as deltas.** `WorkflowExecution.Emit` reduces `ActivityCompleted` / `VariablesMerged` to the keys the merge changes (`WorkflowVariablesState.ChangesFrom`, compared by `VariableValues.AreEqual`). `Apply` merges key by key, so the state is identical live and on replay; a script task that returns its whole scope journals only what it wrote. Entry points cap incoming variables at `Fleans:Variables:MaxSizeBytes` (JSON bytes, default 1 MiB): `WorkflowInstance.EnsureVariablesWithinLimit` throws `ArgumentException` (REST 400; a script or custom task fails its activity; 1140, Warning) before anything is applied. `FailActivity` is the exception: the failure must land, so it drops oversized variables instead.
- **The append is idempotent (#877).** `AppendEventsAsync(instanceId, events, expectedVersion, batchId)` stores the batch id with the row. When the insert collides on `(InstanceId, FirstVersion)`, the store reads that row's `BatchId` (only on a conflict, never on the common path): the same id means this batch was already stored by a try whose success was lost — a timeout or dropped connection after the commit — so it returns `true` without appending; another id means another writer, `false`. The grain picks the id in `ApplyUpdatesToStorage` the first time it sees a batch and keeps it for Orleans' retries in `_unconfirmedBatches`, recognising them by the event objects (the adaptor resends its pending entries, so the failed try's events come first, followed by any raised since). A retry resends each earlier try exactly as it was, with its id and at its version, and appends only the newer events as a new batch. The tries are dropped once the append succeeds or returns `false`, never on a throw — a throw may have been stored.
- **The append is the commit.** `ApplyUpdatesToStorage` returns `true` once the append succeeds; the projector notification and the snapshot write after it log on failure and never throw. Throwing there makes Orleans' `CustomStorage` adaptor retry the same batch at the new version, which appends it twice. A failed `InstanceAdvanced` publish (1132, Warning) is retried by a keep-alive grain timer with doubling delays from 2 s, because the failed one may be the instance's last. On success it logs 1134. After 8 attempts (~8.5 min) it gives up (1135, Error) so a publish that always fails cannot pin the grain, and the next activation asks again instead. A failed snapshot write logs 1131 at Error with the tail length: snapshots that keep failing let the tail grow past `MaxEventsPerLoad`, and then the instance cannot activate.
- **Snapshots are a cache.** `WorkflowSnapshots` holds one row per grain: the **full** `WorkflowInstanceState` (Orleans binary serialization) and the version it covers. A new snapshot is written once `Persistence:SnapshotInterval` (default `100`) events were appended since the last one. Activation loads it and replays the tail. A failed snapshot read is not worked around: Orleans' adaptor retries `ReadStateFromStorage` with backoff, so the activation waits (pre-1.0, a snapshot from an older build means "use a fresh database"). Anything that crosses into state must be Orleans-serializable: copy caller lists into `List<T>` (see `UserTaskMetadata.Initialize`).
- **The read model is built off the hot path (#861).** The grain writes only the journal. After an append that changes the read model it publishes `InstanceAdvanced(InstanceId, Version)` (`Fleans.Domain.Abstractions`) on the `events.InstanceAdvanced` stream namespace, one stream per instance (so per-instance order holds on Redis and Kafka alike). `WorkflowInstanceProjector` (`Fleans.Application/Projections/`, an `[ImplicitStreamSubscription]` grain keyed by the instance id, `[WorkerPlacement]`) consumes it: it rebuilds the state with `JournalReplay.LoadAsync` — latest snapshot plus tail, the same code `ReadStateFromStorage` uses; while the notified version is below `SnapshotInterval` the instance has no snapshot yet, so it skips the snapshot read and replays the journal in one read (falling back to the snapshot if the head has meanwhile passed `MaxEventsPerLoad`, #903) — and calls `IWorkflowStateProjection.WriteAsync(id, state, version)` at the journal's head. The grain never loads state from the read model; it reads the row back only to compare it on activation (below). No new deployable: the projector runs on the worker silos (`worker-*` / `combined-*`), next to the script executor, so projection reads and writes stay off the core silos — see [placement-and-roles.md](placement-and-roles.md#read-model-projector-on-worker-silos-861).
- **Coalescing and idempotency.** The stream delivers one notification at a time per instance; each projection goes to the head, so notifications that queued behind it are at or below the projector's `_projectedVersion` and are skipped (4071, Debug) — a burst costs one or two projections. Each `WorkflowInstances` row stores `ProjectedVersion` (shadow column), and a write lands only past it: running rows are upserted with `ON CONFLICT ("Id") DO UPDATE … WHERE "WorkflowInstances"."ProjectedVersion" < excluded."ProjectedVersion"`, a completed one checks the loaded row's version first, and loads the stored details to diff only when that row was already completed (details are written only together with `IsCompleted`). So a redelivery, a reactivated projector or a stale duplicate activation never rolls the row back. A failed projection (4072, Warning) is rethrown, and the stream redelivers it (Orleans retries delivery for `MaxEventDeliveryTime`, 1 min by default, then drops it — the activation check below is the safety net). See guard 12 in [`invariants.md`](invariants.md#stream-redelivery-idempotency).
- **Batched across instances (#861).** The projector does not write by itself: it awaits `ProjectionBatcher.WriteAsync` (`Fleans.Application/Projections/`, a silo singleton). The batcher queues the writes of every projector on the silo and hands them to `IWorkflowStateProjection.WriteBatchAsync` in batches. A batch starts when one of `Fleans:Projector:MaxConcurrentBatches` (default 4) write slots is free. It takes what is queued, then waits up to `MaxBatchDelayMs` (default 20) for more, up to `MaxBatchSize` (default 64, 1–1000; 1 = unbatched). The queue holds `MaxBatchSize × MaxConcurrentBatches` writes; past that `WriteAsync` waits to enqueue, which holds back the projector's stream delivery (back-pressure). `EfCoreWorkflowStateProjection.WriteBatchAsync` keeps the newest write per instance (a multi-row upsert may not touch a row twice), sorts by id (concurrent batches lock shared rows in one order), then writes all running rows as **one** multi-row `INSERT … ON CONFLICT DO UPDATE … WHERE` and the completed ones (rows plus details) with one split query and one `SaveChanges`. The statement is built from EF metadata, and each parameter comes from its column's type mapping, so value converters apply. PostgreSQL and SQLite (3.24+) both accept it, so there is no per-provider SQL. The two parts commit separately; that is safe because a failed batch is retried whole and the version guard turns the repeated upsert into a no-op. **At-least-once holds:** `WriteAsync` completes only when its batch is durable, so the stream notification is acknowledged after the write. A failed batch (4076, Warning) fails every write in it: each projector rethrows (4072) and its stream redelivers. A batch that keeps failing on one bad row holds back its batch-mates until delivery gives up, and the activation check below catches them up. Cost, measured by `ProjectionTransactionCountTests` (an EF interceptor counting commands and commits, 64 instances × 3 projections): unbatched, 3 write transactions per instance (4 before the upsert replaced update-then-insert); batched, 3 per 64 instances (~0.05 per instance). On PostgreSQL that is 7 commands in all: two upserts, the four reads of the split query and one `SaveChanges`, against 448 unbatched.
- **A notification only when the row changes (#878).** `WorkflowInstanceRow` is a record of the row's scalar columns; `WorkflowInstanceRow.From(state)` builds it, and record equality is the "changed?" check — no hand-kept list of event types. Only `WorkflowStarted`, `ParentInfoSet`, `ExecutionStarted` and the three terminal events change it, so a running instance publishes 2–4 notifications, not one per append. After each append, `TryPublishAdvanced` compares the state's row with `_publishedRow` (the last row this activation asked for, or read on activation). A completed instance publishes on every append (its details are projected too; appends after completion are rare). `From` truncates timestamps to microseconds, Postgres's precision, so a row read back compares equal. `WorkflowInstanceRow_CoversEveryMappedScalarColumn` fails when the state gains a mapped column the record lacks — add it to both.
- **Details only once the instance completes.** A running instance projects only its row — status, timestamps, business id: what lists and filters need. Its details (entries, variable scopes, condition results — what `GetStateSnapshot` serves) are written in the same `SaveChanges` that sets `IsCompleted`, so a finished instance is shown without activating its grain. `WorkflowQueryService.GetStateSnapshot` reads that flag: completed → the read model; no row yet or not completed yet → `IWorkflowInstanceGrain.GetStateSnapshot()` (a grain that was never started — no `CreatedAt` — is a 404). So the state endpoint reads its own writes even though the projector runs behind; instance lists (`GetInstancesByKey*`) and `GetBpmnXml`'s row lookup are eventually consistent (`GetBpmnXml` falls back to the grain for the definition id). Both snapshot paths build the response with `InstanceStateSnapshots.From`, which stamps `StateVersion` (the grain's journal version, or the row's `ProjectedVersion`) and `IsFromReadModel`; the listings' `WorkflowInstanceInfo.StateVersion` is the row's `ProjectedVersion`. The admin UI shows them ("vN · live / read model" in the instance page header, and a "State version" column on instance lists) so the projector's lag is visible, not hidden. Members with no read-model columns (`UserTasks`, `CompensationLog`, `TransactionOutcomes`, `PendingOperations`, …) live only in the snapshot and journal. `Variables` has a JSON `ValueComparer`, so a completed instance's unchanged scopes are not rewritten.
- **Activation is the safety net.** `ReadStateFromStorage` reads the stored row (`ReadRowAsync`, `null` when absent) in parallel with the snapshot and the events, so the check adds no round trip. If it differs from `WorkflowInstanceRow.From` of the replayed state — a notification lost between append and publish (silo crash), to exhausted retries, or dropped by the stream, or simply still on its way — or could not be read (1136), the grain publishes `InstanceAdvanced` again (1133). Harmless when the projector was merely behind: it projects only past what it wrote.
- **Nothing else may depend on the read model.** Grain storage written in the same turn as an append runs before the instance's row exists, so no other table has a foreign key to `WorkflowInstances` (`UserTasks` lost its FK in `DropUserTaskWorkflowInstanceForeignKey`; with it, user tasks failed to register and every user-task command returned 404). Only the projection's own detail tables (entries, variable scopes, condition results, …) reference the row. Regression test: `EfCoreUserTaskGrainStorageTests.Write_BeforeTheInstanceRowIsProjected_Succeeds`.
- **Tests wait for the projector.** `WorkflowTestBase.WaitForProjection(ids)` polls the test-only inspector's `IsProjectionCaughtUp` (stored row equals the grain state's row) — use it before reading lists or the `WorkflowInstances` tables directly; `GetStateSnapshot` needs no wait. E2E specs poll lists with `FleansApiClient.WaitForInstancesPageAsync`.
- **A snapshot is exactly the state at its version.** An `[AlwaysInterleave]` durable enqueue can confirm while the main turn has applied events to `State` but not drained them; `ApplyUpdatesToStorage` then skips the notification and the snapshot (the main turn's drain does them). `EnqueueDurable` itself changes `State.PendingOperations` before its append and can interleave with another append's awaits. Log writes run one at a time, so it is still in flight (`EnqueueInFlight`: its `_enqueueLock` is held) when that append decides on a snapshot, and the snapshot is skipped. The read model does not project `PendingOperations`, so it is unaffected.
- **`TransitionState` applies nothing (#846).** `State` is the adaptor's confirmed view, which the aggregate mutates before each `RaiseEvent`; `ReadStateFromStorage` replays the journal itself. Orleans calls `TransitionState` with every batch it just appended, so applying there applied the batch twice — it used to be skipped under a `_draining` flag that an interleaved `EnqueueDurable` could clear while the main turn's batch was still appending. Keep it a no-op; there is no other caller (the grain never reads `TentativeState`).
- **A re-read keeps the live state unless another writer moved the journal (#845, #877).** A failed or conflicting append makes the adaptor re-read the state, swap `State` for the object `ReadStateFromStorage` returns, then retry the batch. On an activated grain it reads only the events past `_journalVersion`: none → it returns the live `State`, which already holds the batch (1138, Warning). Some, after a try that threw → they may be that try, stored after all: it returns the live `State` at `_journalVersion` and the retry resends the try with its batch id, which the store confirms (1139, Warning). Some, after a conflict (`false`) → the journal moved without this activation; the re-read state is returned, the activation retires (1137, Error, `WorkflowInstanceStaleException` for new calls) and skips the projector notification and the snapshot write until the next activation replays the journal. A try that threw but lost to another writer reaches 1137 one re-read later, when its retry conflicts. See guard 10 in [`invariants.md`](invariants.md#stream-redelivery-idempotency).
- **Replay is deterministic.** Every journaled event derives from `WorkflowEvent`, whose `OccurredAt` is stamped by `WorkflowExecution.Stamp` (called by `Emit` and by the grain's durable enqueue, which raises its event directly). The journal is typed on `WorkflowEvent` (`JournaledGrain<WorkflowInstanceState, WorkflowEvent>`, `IEventStore`), so nothing else can be journaled. `Apply` handlers take ids and times only from the event (state transition methods take the timestamp as a parameter), so replay rebuilds exactly the live state. Never read the clock or call `Guid.NewGuid()` in an `Apply` path.
- **The definition is not part of the state (#860).** State holds only `ProcessDefinitionId`. A deployed version never changes, so an activation takes its `WorkflowDefinition` from `WorkflowDefinitionCache`, a silo singleton keyed by `ProcessDefinitionId`: the first activation of a version in a silo calls `IProcessDefinitionGrain.GetDefinitionById` (6050, Debug), every later one shares that object. `WorkflowDefinition` is `[Immutable]`, so in-silo grain calls pass it by reference instead of deep-copying the graph — never edit a definition's lists after parsing (build a changed one with `with`). Entries are never evicted. `ProcessDefinitionGrain` loads its versions without `BpmnXml` (`IProcessDefinitionRepository.GetByKeyAsync` leaves it empty); the editor reads the XML through `IWorkflowQueryService`.
- **A terminal instance deactivates once idle (#860).** At the end of a drain, an instance that is completed (or failed) with no queued or journaled pending events, no undrained events and no projection retry calls `DeactivateOnIdle` (1148, Debug) instead of staying resident for the collection age. A later call (a late callback, `GetStateSnapshot`) reactivates it from the journal. An instance started from a definition that has no `ProcessDefinitionId` (only tests do this) could not reload its definition, so it is left to normal collection.
- **Retention (#862).** Nothing deletes a finished instance automatically. `POST /Instances/purge` → `IWorkflowInstancePurgeService` (`EfCoreWorkflowInstancePurgeService`) selects finished instances from the read model (`IX_WorkflowInstances_CompletedAt`, oldest first; children of running parents skipped), deletes each journal and snapshot through `IEventStore.DeleteInstanceAsync(instanceId)` — the journal stays accessed only by `InstanceId` — and then the batch's read-model rows (user tasks included) in one transaction. Journal first, so an interrupted purge is finished by the next call. A new per-instance table must be added to `DeleteReadModelAsync`. A late `InstanceAdvanced` for a purged instance finds no journal and is skipped (4074), so it cannot resurrect the row; a projection already past its journal read when the purge runs can still write the rows back (narrow race, left as is). Runbook: [`docs/runbooks/instance-retention.md`](../runbooks/instance-retention.md).
- **Pre-1.0:** this layout needs a fresh database (Postgres: the `CompactJournal` migration; SQLite: delete the dev DB file). ## Journal store: separate database, Citus

The journal and snapshots have their own context, `FleanJournalDbContext` (#879), used only by `EfCoreEventStore`; `FleanCommandDbContext` no longer maps them. Read model and every other grain state stay on the main database.

- **Configuration.** `Persistence:Journal:Provider` (`Postgres` | `Citus` | `Sqlite`) and `ConnectionStrings:fleans-journal`. An empty provider means `Postgres` — except on a SQLite main database without `fleans-journal`, where it means `Sqlite`, so dev, Aspire and the E2E runs need no config. Without `fleans-journal` the journal context points at the main database (Postgres: the main `NpgsqlDataSource`). A journal provider of another family than the main one (PostgreSQL journal next to SQLite) requires `fleans-journal`. `FleansPersistenceExtensions.ConfigureJournal` resolves it; a separate Postgres journal gets its own data source, keyed `fleans-journal` in DI. A `journal` health check sits next to `database`.
- **Schema.** `EnsureDatabaseSchemaAsync` runs the main context first, then the journal context with the same advisory lock on its own connection. Postgres: the journal migrations (`Migrations/Journal`, history table `__EFJournalMigrationsHistory`, `UseFleansPostgresJournal`). On a shared database the command chain creates the journal tables and `MoveJournalToOwnContext` drops them again (pre-1.0: no upgrade path, an existing journal is dropped — use a fresh database), then `InitialJournal` recreates them. SQLite: `SqliteSchemaInitializer.EnsureCreatedIgnoreRaces` creates the context's tables when the file already has another context's (plain `EnsureCreated` creates nothing in a non-empty file). `SqliteModelCustomizer` skips the journal context.
- **Citus** (`Persistence:Journal:Provider=Citus`): after the journal migrations, `CitusJournal.DistributeAsync` runs `create_distributed_table` on `WorkflowEventBatches` by `InstanceId` into `Persistence:Journal:Citus:ShardCount` shards (default 128, validated 1–64000 by `FleansPersistenceOptionsValidator`) and on `WorkflowSnapshots` colocated with it — once; distributed tables are skipped, so a changed shard count does not reshard them. It throws when the `citus` extension is missing. Both primary keys start with `InstanceId`, as Citus requires; the append's `(InstanceId, FirstVersion)` conflict and the snapshot upsert stay single-shard, so the store needs no Citus-specific code. Without `fleans-journal`, `Citus` distributes the tables inside the main database (a Citus coordinator). Licence: AGPL-3.0 — fine unmodified.
- **The shard-key invariant** — see [`invariants.md`](invariants.md#journal-tables-are-accessed-by-instanceid-only): every journal command filters or keys by `InstanceId`, and `InstanceId` stays a random Guid v4. `EfCoreEventStoreTests.EveryJournalCommand_IsKeyedByInstanceId` records the store's SQL and fails on an unkeyed command.
- **Contract tests.** `EventStoreContractTests` (abstract, `Fleans.Persistence.Tests`) holds the `IEventStore` semantics through the interface only: contiguous versions and gap detection, conflict → `false`, a snapshot exactly at its version, the idempotent retry (#877), the purge `DeleteInstanceAsync` (#862), the `MaxEventsPerLoad` guard. `EfCoreEventStoreContractTests.cs` runs it on a journal-only database per provider: SQLite (in-memory), PostgreSQL and Citus (`citusdata/citus:12.1`, single node) — the last two under `TestCategory=Postgres`. A new provider derives a `[TestClass]` and implements `CreateStoreAsync`; layout tests stay in its own class (`EfCoreEventStoreTests`). `EnsureDatabaseSchemaTests` applies the schema through the hosts' code path, default and with a separate Citus journal.
- **YugabyteDB** (YSQL) is the documented alternative, not a provider: it needs retries on snapshot-isolation conflicts and squashed migrations.

## `Persistence:MaxEventsPerLoad` safety valve (default `1000`)

`EfCoreEventStore.ReadEventsAsync` throws `InvalidOperationException` if the unread event delta exceeds this cap, surfacing broken snapshotting before it OOMs the silo. It must be greater than `Persistence:SnapshotInterval` — `FleansPersistenceOptionsValidator` fails startup otherwise. Passing that check is not a guarantee: a very large batch appended just before a crash, or failing snapshot writes (1131), can still leave a longer tail. Increase via the `Persistence__MaxEventsPerLoad` env var for deployments with legitimately large deltas.

`FleansPersistenceOptions` lives in `Fleans.Persistence` (not `Fleans.ServiceDefaults`) to avoid a circular project reference.

## User-task list filter pushdown (audit #415)

`GetPendingUserTasks(assignee, candidateGroup, page)` pushes the assignee/candidateGroup filter to SQL on PostgreSQL via JSON-encoded `LIKE` patterns in raw SQL (`FromSqlInterpolated`); SQLite retains the existing in-memory filter.

`EF.Functions.Like` against a value-converted column (the JSON-serialized `IReadOnlyList<string>`) is not usable — EF applies the value converter to the LIKE pattern constant. **Use `FromSqlInterpolated` for any future column-level JSON filter on the same pattern.**

Strategy: `IUserTaskFilterStrategy` / `PostgresUserTaskFilterStrategy` in `Fleans.Persistence` / `Fleans.Persistence.PostgreSql`.
